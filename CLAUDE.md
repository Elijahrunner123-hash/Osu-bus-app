Guidance for Claude Code (claude.ai/code) working in this repository.

## Repository status

`index.html` is the entire app — no build step, package manager, server, or test suite. The one side file is `tools/fetch-cabs-data.js`, a dependency-free Node script that regenerates the baked-in CABS data literals; run it with `node tools/fetch-cabs-data.js` and paste its output over the generated block in the DATA section. Geolocation needs a secure context, so run it over `http://localhost` (`python3 -m http.server`), not `file://`. Append `?now=ISO` (e.g. `?now=2026-08-24T09:00`) to override the clock for testing arrive/leave logic.

To sanity-check routing without a browser (no browser automation exists in this environment), extract the app's inline `<script>` and run it in a Node `vm` context with `document`/`localStorage`/`fetch`/`navigator` stubbed; top-level code is DOM-free and `init()` only runs when `document` exists, so the pure functions (`currentTripContext`, `transitLeg`, `planTrip`) can be called directly.

## Project overview

**CABS Parking Router** — a personal (single-user, v1) tool that, given a weekly OSU class schedule and the user's live location, computes the fastest route between car and class over parking lots (Carmack vs. Buckeye), walking, and CABS (Campus Area Bus Service) legs, and shows it on a map. Time of day auto-selects the direction: **arrive** (drive to the best lot, transit to class) before class, **leave** (transit back to the parked car) during/after.

Full design rationale, data shapes, and research TODOs live in `cabs-router-plan.md` — read it before architectural changes; the notes below only cover what's implemented.

## Architecture

`index.html` is organized into labeled sections so any one can be swapped without touching the others. Keep data-fetching (WALKING, REALTIME, LOCATION) out of render functions.

1. **DATA** — `permits`, `lots`, `buildings`, `schedule` hand-maintained; `routes`, `stops`, `routeStopOrder`, `routePatterns` **generated** from OSU's public bus API by `tools/fetch-cabs-data.js` (see plan §2) — edit the script, not the literals. All 57 official stops are present with the API's own string ids (`"75"`, `"MC7"`, one raw UUID — never coerce to number). `routePatterns` holds each route's Google-encoded polyline, the real road shape the map draws. `buildings` still covers only the Biology 1113 halls. Lot coords are their corresponding bus-stop coords, not the lots' centers. Design shapes to generalize beyond the single CXC permit / two-lot case (`permits.lots` is a list) per plan §1/§8.
2. **WALKING / DRIVING** — `routeLeg(a, b, profile)` returns duration + path geometry, trying three sources in order: **OpenRouteService** (only if the user set a key), then **Valhalla on FOSSGIS's public instance** (`valhalla1.openstreetmap.de`, no key, no account), then a straight-line haversine estimate. Valhalla is the default because it needs no setup, is genuinely profile-aware (~5 km/h `pedestrian` vs ~22 km/h `auto`), and — unlike ORS — returns CORS headers on error responses, so the browser can read the status. It's called via `GET ?json=` so the request stays preflight-free, and encodes its shape at **6** decimal places, hence `decodePolyline(str, precision)`. It's a donated public instance: keep usage to the 2-3 requests a plan already spends. **ORS's error responses omit `Access-Control-Allow-Origin`**, so a rejected key is indistinguishable from a network failure in the browser — that is why a bad key used to silently produce straight lines. `orsRequestFailed` records that case and `orsNote()` explains it honestly rather than guessing. `walkRoute` memoizes per (from,to) pair; that cache is only valid for the ORS-key state it was computed under, so `invalidateWalkCacheIfKeyChanged()` runs at the top of **both** `routeLeg` and `walkRoute` — including the cache-hit path, which never reaches `routeLeg`. Not MapKit JS, to avoid an Apple Developer account dependency.
3. **REALTIME** — `getNextArrival(stopId, routeId)` is still a stub returning a random 2–12 min value. The real feed is already identified and needs no reverse-engineering: `GET https://content.osu.edu/v2/bus/routes/{CODE}/vehicles` returns live buses whose `predictions[]` carry `stopId` and `timeToArrivalInSeconds` (plan §2). Only this function's internals should change. Note predictions exist *only while buses are running* — an empty `vehicles` array means "no live data", not "no service", and still needs a timetable fallback.
4. **LOCATION & TIME** — `getUserLocation()` wraps the Geolocation API and resolves to a campus-center fallback (flagged `estimated`) on denial rather than rejecting. `currentTripContext(now)` is pure: from `schedule` it picks today's most-relevant class and returns `{ mode: "arrive"|"leave", entry, today }`.
5. **ROUTING** — two phases, and keeping them separate is the point. **Search** (`transitLeg`) runs entirely on local haversine estimates with no network at all, comparing a direct walk against the best board→ride→alight bus option (15 min walk cap) and attaching the bus leg's real geometry from `busGeometry()`. **Refine** (`refineItinerary`) then spends real routing calls on the chosen itinerary only — at most a drive leg plus two walk legs — and recomputes the total. Searching with real calls is what previously fired ~117 ORS requests per plan against a 40/min ceiling, so every leg silently fell back to a straight line; don't reintroduce a network call inside the search loops. `getNextArrival` is likewise funnelled through `nextArrival()`, memoized per plan and cleared by `planTrip`. `planTrip({ mode, origin, entry, permit })`: **arrive** estimates a drive to each candidate lot, keeps the fastest, persists the winning lot to `localStorage`, then refines; **leave** routes from `origin` back to that remembered lot. `scheduledRideTime` is a static haversine estimate, not calibrated to real bus speed.
6. **MAP** — Leaflet + CARTO Voyager tiles (no key/account, Apple-Maps-like). One polyline per leg: drive solid, walk dotted, and the bus leg drawn along the route's real road-following shape in that route's official CABS colour (`routeColor()` picks the light/dark variant to match the viewer's theme). `busGeometry(routeCode, board, alight)` decodes the route's polyline and slices it between the two stops — most routes publish paired inbound/outbound patterns so the correct direction is whichever runs board→alight; WMC is a genuine loop and wraps past the end of the shape; MC publishes only its Doan→Carmack direction, so the return trip walks the same shape reversed. Returns `null` if nothing fits, and the map falls back to a straight line.
7. **UI** — full-screen map with a draggable frosted bottom sheet (Apple styling, San Francisco via `-apple-system`, light/dark). On load it gets location + trip context and routes automatically; an Arrive/Leave segmented control and class chips override the time-of-day guess.

## Key constraints from prior decisions

- OSU publishes an unauthenticated, CORS-enabled bus API at `content.osu.edu/v2/bus` (plan §2). It needs no key, no OSU login and no proxy capture, which retires both the Proxyman plan and the "what if it needs the user's OSU credentials" pause-point.
- Treat that API as the source of truth for routes and stops. Where it disagrees with hand-entered values, the API wins — the hand-transcribed Arps Hall entry claimed five routes when the API serves two.
- Prefer baked-in generated data over fetching at load, so the app still works offline; regenerate via `tools/fetch-cabs-data.js`.
- Search on cheap local estimates, spend real routing calls only on the chosen itinerary. ORS's free tier (40 req/min) is small enough that a search-time network call silently degrades every result to a straight line.
- Prefer keyless, CORS-clean services the user never has to configure — CARTO tiles, the OSU bus API, and now Valhalla all follow this. A provider that hides its error status behind a missing CORS header (ORS) will fail silently and waste an afternoon; check `access-control-allow-origin` on an *error* response, not just a successful one, before adopting one.
- Verify browser-facing behaviour in a real browser. `curl` does not perform CORS, and a Node `fetch` stub does not enforce it, so both happily pass while the page fails.
