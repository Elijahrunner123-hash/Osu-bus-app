Guidance for Claude Code (claude.ai/code) working in this repository.

## Repository status

`index.html` is the entire app — no build step, package manager, server, or test suite. The one side file is `tools/fetch-cabs-data.js`, a dependency-free Node script that regenerates the baked-in CABS data literals; run it with `node tools/fetch-cabs-data.js` and paste its output over the generated block in the DATA section. Geolocation needs a secure context, so run it over `http://localhost` (`python3 -m http.server`), not `file://`. Append `?now=ISO` (e.g. `?now=2026-08-24T09:00`) to override the clock for testing arrive/leave logic.

To sanity-check routing without a browser, extract the app's inline `<script>` and run it in a Node `vm` context with `document`/`localStorage`/`fetch`/`navigator` stubbed; top-level code is DOM-free and `init()` only runs when `document` exists, so the pure functions (`currentTripContext`, `transitLeg`, `planTrip`) can be called directly. For browser-facing behaviour, drive the page for real: Playwright's bundled Chromium is installed (`~/Library/Caches/ms-playwright`), so a short `playwright-core` script can load `http://localhost:8765`, grant geolocation, and abort routes (`page.route("**unpkg.com/**", r => r.abort())`) to test provider and CDN failures. The landing screen is now the browse view (§7) — it renders as soon as `#sheetContent` stops being the initial "Loading live buses…" placeholder, with no network wait, so testing the *planning* path (routing tiers, error/hang fixtures, etc.) requires clicking `[data-generate-route]` first and then polling `#sheetContent` until it stops saying "Finding your best route…". The Playwright **MCP server** does not work here — it is configured for channel `chrome` and Google Chrome isn't installed; use `playwright-core` directly instead.

## Project overview

**CABS Parking Router** — a personal (single-user, v1) tool that, given a weekly OSU class schedule and the user's live location, computes the fastest route between car and class over parking lots (Carmack vs. Buckeye), walking, and CABS (Campus Area Bus Service) legs, and shows it on a map. Time of day auto-selects the direction: **arrive** (drive to the best lot, transit to class) before class, **leave** (transit back to the parked car) during/after.

Full design rationale, data shapes, and research TODOs live in `cabs-router-plan.md` — read it before architectural changes; the notes below only cover what's implemented.

## Architecture

`index.html` is organized into labeled sections so any one can be swapped without touching the others. Keep data-fetching (WALKING, REALTIME, LOCATION) out of render functions.

1. **DATA** — `permits`, `lots`, `buildings`, `serviceSchedule` hand-maintained (`serviceSchedule` is CABS's published hours/headways transcribed from ttm.osu.edu — the API has no timetable endpoint; a route absent from a time band isn't running and is dropped from the search rather than given an invented wait); `routes`, `stops`, `routePatterns` **generated** from OSU's public bus API by `tools/fetch-cabs-data.js` (see plan §2) — edit the script, not the literals. All 66 official stops are present with the API's own string ids (`"75"`, `"MC7"`, one raw UUID — never coerce to number). `routePatterns` holds each route's Google-encoded polyline, the real road shape both the route view's bus leg and the browse view's faint route-shape layer (§6/§7) draw. `buildings` still covers only the Biology 1113 halls. Lot coords are their corresponding bus-stop coords, not the lots' centers. Design shapes to generalize beyond the single CXC permit / two-lot case (`permits.lots` is a list) per plan §1/§8.
   `schedule` is now only the **seed**: from the first run onward the working copy lives in `localStorage` (key `cabsSchedule`), edited via the Settings schedule editor (§7). `loadSchedule()`/`saveSchedule(entries)` are the only sanctioned readers/writers — every consumer (`currentTripContext`, `chipsHtml()`, `renderSheet()`'s class list, the chip click handler) goes through `state.schedule` (populated by `loadSchedule()` at `init()` and refreshed on every schedule Save), never the bare `schedule` const. `loadSchedule()` re-seeds only for genuinely unusable data — a missing key, unparseable JSON, or a non-array — because a broken localStorage value must never break startup. It does **not** re-seed for an empty array: deleting every class is a legitimate user state that the app already handles (`currentTripContext` returns `entry: null` and the sheet says "No class today"), and re-seeding there silently resurrected the developer's own seeded classes the first time the user cleared them, while leaving the Settings editor showing four rows against a stored `[]`. Individual entries failing `isValidScheduleEntry()` (valid `DAY_NAMES` day, `HH:MM` start/end, and a `building` id that exists in `buildings`) are **filtered out**, not treated as grounds to discard the whole schedule — one stale building id must not wipe every class the user entered. Whatever survives that filter is what both the Settings editor and the planner see; they must never disagree (verified by the "corrupt `cabsSchedule`" case in `verify-schedule.mjs`, and by `harness-nonet.mjs`'s stubbed in-memory `localStorage`, which starts empty and exercises the same seed-on-first-run path). Route toggle state (§6/§7) is the one other piece of durable state, `enabledRoutes`/`localStorage["enabledRoutes"]`, loaded by `loadEnabledRoutes()` — unlike the schedule, an intentionally-empty selection (every route toggled off) is honored rather than re-seeded, since there's no meaningful corrupt-vs-deliberate ambiguity for a plain array of route codes.
2. **WALKING / DRIVING** — `routeLeg(a, b, profile)` returns duration + path geometry, trying three tiers in order: **FOSSGIS's public OSRM instances** (`routing.openstreetmap.de`, no key, no account), then **Valhalla's public instance** (`valhalla1.openstreetmap.de`, no key, no account), then a straight-line haversine estimate. Unlike the old `router.project-osrm.org` demo (which only ever had its car profile loaded, so every profile returned byte-identical car-road results), FOSSGIS runs genuinely distinct routed instances per profile — `routed-foot` for `foot-walking`, `routed-car` for `driving-car` — so `routed-foot`'s reported duration is a real pedestrian time over an actual footpath/sidewalk network (~4.5 km/h), not a car-road distance dressed up with a walking-speed formula; a walk can legitimately beat the equivalent drive because a pedestrian cuts through where a car has to go around. `estimateWalkMinutes(km)` therefore no longer feeds a real provider's result at all — it's purely the straight-line fallback's speed model (tier 3) and `estWalk`'s cheap local prefilter (§5), never a derivation on top of `routed-foot` or Valhalla. FOSSGIS is called via `GET .../route/v1/{foot|car}/{lng},{lat};{lng},{lat}?overview=full&geometries=polyline6` (`fossgisLeg`) and Valhalla via `GET valhalla1.openstreetmap.de/route?json=<encoded body>` with `costing: "pedestrian"`/`"auto"` (`valhallaLeg`, GET-with-`?json=` to stay preflight-free, POST is not used) — both encode their shape at **6** decimal places, hence `decodePolyline(str, precision)`; Valhalla nests its shape per-leg (`trip.legs[].shape`), concatenated before decoding. Both are donated public instances: keep usage to the couple of requests a plan already spends. Both providers' error responses **are** CORS-readable (HTTP 400 with a legible JSON body), so a genuine failure is distinguishable from a network outage — verify this on an *error* response, not just success, before trusting a new host. **Every provider call is bounded by `fetchWithTimeout(url, opts, ROUTING_TIMEOUT_MS)`** — a provider can accept the TCP connection and simply never answer (Valhalla did exactly this during an earlier outage, hanging `/route` *and* `/status` past 12s — the outage has since cleared, and Valhalla is kept as tier 2 specifically so a future FOSSGIS outage doesn't have to fall straight to a straight line), which left `planTrip()` awaiting a promise that never settled and stranded the UI on "Finding your best route…" forever, with `refresh()`'s `try/catch` never firing. An abort is re-thrown as a plain `Error("timeout after Nms")` so the fallback chain and `estimateReason` (`"timeout"` / `"ratelimit"` / `"unreachable"`, via `classifyRoutingError`) both read sensibly. Each tier gets its **own** session circuit breaker (`fossgisCircuitOpen`, `valhallaCircuitOpen`) — a plan calls `routeLeg()` up to three times, so a dead FOSSGIS shouldn't also force three redundant Valhalla timeouts, but a dead FOSSGIS also shouldn't stop Valhalla from being tried; only when a leg falls all the way through to `estimateLeg` does `usedEstimateFallback`/`estimateReason` get set — an intermediate tier's failure just trips its own breaker and falls through silently. Both breakers only reset on reload. `walkRoute` memoizes per (from,to) pair for the page session. Not MapKit JS, to avoid an Apple Developer account dependency. **OpenRouteService is gone entirely**, along with the API-key Settings field: its error responses omit `Access-Control-Allow-Origin`, so a rejected key was indistinguishable from a network failure in the browser, and it required an account the user had to go register for.
3. **REALTIME** — live arrivals from `GET content.osu.edu/v2/bus/routes/{CODE}/vehicles`. **One request covers every stop on a route**, so `warmPredictions()` fetches per route (≤9) into a 25s TTL `predictionCache`, and `nextArrival()` is then a synchronous lookup — the search loop must never fetch. Read `timeToArrivalInSeconds`; `predictionCountdown` is the string `"DUE"` when a bus is pulling in. Predictions carry no pattern of their own, so each inherits its **parent vehicle's** `patternId` — that is what makes direction filtering possible. A prediction's `destination` string is *not* a usable direction hint and is deliberately discarded: at University Hospital every MC prediction reads "Medical Center", including the pattern-2016 buses heading back to Carmack. Predictions exist *only while buses are running*: an empty `vehicles` array means "no live data", not "no service", and falls through to `serviceSchedule`. WMC/ACK/MM never publish predictions at all — only positions.
   Each `predictionCache` entry now also records **why** there's nothing usable: `status` is `"ok"` when the fetch itself succeeded (whether or not it had anything to report) or `"failed"` when the request never came back at all — network error, CORS block, or timeout. This distinction used to not exist: on a `file://` origin, every `content.osu.edu` request is CORS-blocked (`fetch` throws before `res.ok` is ever checked), `warmPredictions()` caught the error and stored nothing, and `nextArrival()` had no way to tell that apart from "this route genuinely isn't running" — so it silently fell back to the timetable *and* the UI claimed "no buses are reporting", which was false. `fetchRoutePredictions()` also returns each route's raw `vehicles`, each carrying its live `lat`/`lng`/`heading` plus a **pre-computed projection** (`proj: { pattern, index, km }`) onto whichever of the route's patterns it's running — computed once per vehicle, right here, per warm cycle (`projectVehicleOnRoute()`, §5). A route's `/vehicles` feed can report `patternId: ""` for every vehicle (confirmed live for WMC/ACK/MM) even though the route has one unambiguous pattern; `projectVehicleOnRoute()` falls back to that lone pattern when there's no direction to disambiguate, which is what makes those three routes' vehicles projectable at all.
   `nextArrival(stop, routeCode, pattern, when, liveAllowed)` (now takes the stop and pattern **objects**, not bare ids, so it can drive a stop→pattern projection when needed) tries four sources in order, so a fabricated number can never outscore a real one and a rougher live one can never outscore a better live one:
   1. A real API prediction for `stop`, filtered by `pattern.id` — `live: true`.
   2. A **position-derived ETA** (`derivedArrival()`, §5) from the nearest upstream vehicle actually on `pattern` — `live: true, derived: true`. A fallback, never a replacement: it diverges from the API's own predictions when a bus is dwelling at a stop (prototyped against live data: tracks well in general — 12/12.6, 7/7.0, 9/8.9 min API-vs-derived — but a dwelling bus showed 15/10.1 and 9/4.1). This is what makes WMC/ACK/MM usable for routing at all, since they publish positions but never predictions and have no `serviceSchedule` entry either — they stay live-only by design; don't invent timetable data for them.
   3. Neither of the above found anything for this exact stop/pattern, but the route has a live signal right now (predictions somewhere, or vehicles on the road) — the full `headway` (not half, which used to be systematically optimistic enough to beat real countdowns), tagged `reason: "no-bus-inbound"`.
   4. No live signal at all this cycle — `headway / 2`, the honest average wait for an unsynchronised rider — tagged `reason: "no-live-data"` (feed answered but empty, or live data wasn't requested) or `reason: "unreachable"` (the feed itself never answered: network/CORS/timeout — the `file://` case). `arrivalNote()` renders three different sentences from these, because "no buses are reporting" and "we couldn't reach the feed to ask" are different claims and used to be conflated into the first, wrong one.
   **Performance**: `derivedArrival()` reuses `stopIndexOn()`'s permanent per-(pattern,stop) cache (stops don't move) but must never cache a vehicle's projection the same way — a bus does move, and a reused vehicle id (CABS vehicle ids persist across trips) would otherwise pin it at a stale spot forever. `projectVehicleOnRoute()` is therefore recomputed fresh every warm cycle and stored *alongside* that cycle's vehicles in `predictionCache`, never inside `transitLeg`'s search loop, which calls `nextArrival()` (and so could call `derivedArrival()`) thousands of times per plan — get this wrong and the search becomes visibly slow. `AVG_BUS_KMH` (15) is the one shared constant behind both `derivedArrival()`'s ETA and `scheduledRideTime()`'s static ride estimate, rather than two copies that could drift apart. `VEHICLE_SNAP_KM` (0.5, looser than `PATTERN_SNAP_KM`'s 0.4) bounds how far a live GPS fix may sit off a pattern's shape and still count as "on it".
4. **LOCATION & TIME** — `getUserLocation()` wraps the Geolocation API and resolves to a campus-center fallback (flagged `estimated`) on denial rather than rejecting; `init()` no longer awaits it before first paint (§7) — it resolves in the background and only recentres the map / flips the "estimated" note when it lands. `currentTripContext(now)` reads the stored schedule via `loadSchedule()` (§1 — its only impurity) and picks today's most-relevant class, returning `{ mode: "arrive"|"leave", entry, today }`.
5. **ROUTING** — two phases, and keeping them separate is the point. `transitLeg(from, to, when)` warms the arrival cache for candidate routes **before** its loops, then searches without touching the network. `patternFor(route, board, alight)` decides which direction the bus must be going; `busGeometry` shares that choice so the drawn path and the arrival direction can't disagree. Stop positions along patterns and cumulative distances are memoized permanently (`stopIndexCache`, `cumulativeCache`), which is what makes a direction check affordable in the innermost loop. Live predictions describe *now*, so `liveDataApplies(when)` falls back to the timetable whenever the `?now=` clock is more than 5 minutes off real time — and `renderSheet()` shows `debugClockNote()` whenever `?now=` is set at all, so that state is never silently ambiguous. **Search** (`transitLeg`) runs entirely on local haversine estimates with no network at all, comparing a direct walk against the best board→ride→alight bus option (15 min walk cap) and attaching the bus leg's real geometry from `busGeometry()`. Its comparison, `isBetterCandidate()`, prefers a live candidate over a scheduled one whenever they're within `LIVE_TIE_MARGIN_MIN` (2 min) of each other — **bus-vs-bus only**, because a direct walk carries no wait at all and so must never lose to a slower bus just for having a live countdown, so a fabricated headway-derived guess can't beat a real countdown purely by looking a couple of minutes faster on paper; outside that margin the strictly faster candidate still wins. **Refine** (`refineItinerary`) then spends real routing calls on the chosen itinerary only — at most a drive leg plus two walk legs — and recomputes the total. Searching with real calls is what previously fired ~117 routing requests per plan against a public demo server's rate limit, so every leg silently fell back to a straight line; don't reintroduce a network call inside the search loops. `getNextArrival` is likewise funnelled through `nextArrival()`, memoized per plan and cleared by `planTrip`. `planTrip({ mode, origin, entry, permit })`: **arrive** estimates a drive to each candidate lot, keeps the fastest, persists the winning lot to `localStorage`, then refines; **leave** routes from `origin` back to that remembered lot. `scheduledRideTime` is a static haversine estimate, not calibrated to real bus speed.
6. **MAP** — Leaflet + Esri gray canvas tiles (`services.arcgisonline.com`, no key/account, Apple-Maps-like), in a matching light/dark pair swapped live on `prefers-color-scheme` via `basemapUrl(dark)` + `tileLayer.setUrl()`. Note Esri's `{z}/{y}/{x}` order — row before column, unlike most tile servers — and that both styles serve to z19. **CARTO was the previous provider and had to be dropped**: it ended anonymous access and began stamping "API KEY REQUIRED" diagonally across every tile it served, which is a reminder that a keyless service can revoke that status silently and the failure shows up as pixels, not as an error status. One polyline per leg: drive solid, walk dotted, and the bus leg drawn along the route's real road-following shape in that route's official CABS colour (`routeColor()` picks the light/dark variant to match the viewer's theme). `busGeometry(routeCode, board, alight)` decodes the route's polyline and slices it between the two stops — most routes publish paired inbound/outbound patterns so the correct direction is whichever runs board→alight; WMC is a genuine loop and wraps past the end of the shape; MC publishes only its Doan→Carmack direction, so the return trip walks the same shape reversed. Returns `null` if nothing fits, and the map falls back to a straight line. The map is **optional**: Leaflet comes from a plain unpkg `<script>` tag, so if that CDN fails `L` is undefined — `initMap()` sets `mapUnavailable` and leaves `map` null rather than throwing, every consumer is null-guarded, and the sheet says so via `mapNote()`. Before that guard, the throw escaped `init()` as an unhandled rejection and left the sheet on "Getting your location…" forever.
   **Live bus markers**: `drawVehicleMarkers(routeCode)` draws the chosen itinerary's live vehicles — whatever `predictionCache` last cached for that route (no network call of its own) — as small arrow markers in the route's colour, rotated toward `heading` via a plain CSS `transform: rotate()` on the divIcon's inner element (cheap; no separate rotation logic needed). They live in their own `vehicleMarkers` layer array, separate from `mapLayers` (the route polylines/pins), because they refresh on a different cadence than a re-plan. Both functions are null-guarded on `map` exactly like `drawRouteOnMap()`, so a CDN-failed Leaflet load degrades the same way here as everywhere else.
   **Browse view's map layers** (§7) reuse both of those same arrays rather than keeping parallel ones — whichever view is active owns the map outright. `drawBrowseRoutes()` draws every route in `enabledRoutes` as a thin, low-opacity polyline per pattern (no board/alight slicing — the whole shape, since there's no chosen itinerary yet) into `mapLayers`; `drawBrowseVehicles()` is `drawVehicleMarkers()`'s multi-route sibling, drawing every enabled route's cached vehicles into `vehicleMarkers` in one pass, again with no network call of its own. Switching views (`generateRoute()`/`backToBrowse()`, §7) always calls `clearMapLayers()` + `clearVehicleMarkers()` before drawing its own layers, so the two views can never show a mix of each other's polylines/markers.
7. **UI** — full-screen map with a draggable frosted bottom sheet (Apple styling, San Francisco via `-apple-system`, light/dark). One explicit state variable, `viewMode` (`"browse" | "route"`), decides which half of the app owns the map + sheet; every render/draw path is routed through it, and switching always clears the other view's map layers first (§6) so the two can't fight over either.
   **Browse (the landing view)**: `init()` calls `renderBrowseView()` synchronously — no `await` on geolocation or trip context first, so the map paints at `defaultLocation` immediately and never blocks first paint on either. `renderBrowseSheet()` lists every route (`routeRowHtml()`) with a colour-matched checkbox (`enabledRoutes`, persisted via `saveEnabledRoutes()`), a live vehicle count (`routeCountText()` — a route with none currently running says so rather than disappearing), and a prominent **"Generate route"** button (`.btn-primary`, the one genuinely new CSS class — everything else reuses `.chip`/`.segmented`/`.note`/`.step`). Toggling a route only updates `enabledRoutes` + redraws the map (`drawBrowseRoutes()`/`drawBrowseVehicles()`, §6) — it never re-renders the sheet, so it can't disturb an open Settings panel. `startBrowseTicker()` re-warms all enabled routes' predictions every `PREDICTION_TTL_MS` + 5s, skipping when `document.hidden`, and patches `[data-route-count]` text + redraws vehicle markers in place, same "patch, don't re-render" discipline as the route view's ticker below.
   **Route view**: pressing "Generate route" (`generateRoute()`) clears the browse map layers up front (so a failed plan doesn't leave stray route polylines behind), recomputes `currentTripContext(clockNow())`, and calls the existing `refresh()` → `planTrip()` → `renderSheet()` → `drawRouteOnMap()` path — unchanged except that `renderSheet()` and every one of `refresh()`'s early-exit templates now open with `topRowHtml()`, a `‹ Live buses` chip (`backToBrowse()`, which clears the route's map layers and calls `renderBrowseView()` again) plus, once an itinerary exists, a `Refresh` chip. An Arrive/Leave segmented control and class chips still override the time-of-day guess within this view. A live wait says "Next bus in 4 min", a position-derived one says "~4 min (from bus location)" (still a real-time signal, just a rougher one — see REALTIME §3), and a timetable one says "~5 min (scheduled)"; a non-live wait raises `usedScheduleFallback` (plus `scheduleFallbackReason`, one of `"no-live-data"` / `"no-bus-inbound"` / `"unreachable"`) so `arrivalNote()` can render the matching honest sentence. The bus leg's sub-line also shows live distance-to-boarding-stop when available (`"· bus 0.6 mi away"`, `fmtMi()` on `nearestVehicleDistanceKm()` — the same board-stop-to-nearest-upstream-vehicle distance `derivedArrival()` already computed for its ETA, now exposed as raw km rather than converted straight to minutes). **`refreshBusLeg(result)`** is the one code path behind both the Refresh chip and the ticker: re-warm that route's predictions, recompute wait + `leg.distanceKm`, redraw that route's vehicle markers, and patch `[data-bus-sub]`/`[data-bus-time]`/`[data-total]` — never a re-render, because `renderSheet()` replaces the whole sheet and would close an open Settings panel, drop focus mid-typing and invalidate the drag snap points. `startArrivalTicker()` just calls `refreshBusLeg()` every 30s (skipping when `document.hidden`); the manual button does the same on click.
   **Settings / schedule editor**: `settingsHtml()` renders the existing provider-note `<details>` plus one row per stored class (`scheduleRowHtml()` — day `<select>` matching `DAY_NAMES`, `<input type="time">` start/end storing `"HH:MM"`, and a building `<select>` populated from `buildings`, never free text, since a typo'd id only used to surface later as `planTrip()`'s "isn't in the buildings data" error; an empty `buildings` array renders a message instead of a dead control). `wireSettingsControls()` keeps its own in-memory draft array — add/delete/edit only touch `#scheduleRows`, never the whole sheet, so nothing outside an explicit Save click can lose an unsaved edit. A module-level `settingsOpen` flag, updated on the `<details>`'s `toggle` event and read back into `settingsHtml()`'s `open` attribute, is what lets Save (which does need a full re-render, since the itinerary/total can change) restore the panel to where the user left it instead of silently collapsing it — the same trick both `renderSheet()`'s and `renderBrowseSheet()`'s full re-renders rely on. Save validates every row with the same `isValidScheduleEntry()` §1 uses, persists via `saveSchedule()`, updates `state.schedule`, recomputes `currentTripContext()`, and re-plans (`refresh()`) if `viewMode === "route"` or just re-renders the browse sheet otherwise.
   **No degraded path may leave a spinner up**: `refresh()` races `planTrip()` against `PLAN_DEADLINE_MS`, `init()` wraps its whole body in try/catch (and its call site adds `.catch()`), and the error, no-route and no-class branches all render `topRowHtml()` + chips + settings and call `wireSheetControls()` — markup without that call is dead UI.
   **`file://` detection**: `isFileProtocol()` checks `location.protocol === "file:"` and, when true, every content branch (`renderSheet()`, `renderBrowseSheet()`, all three of `refresh()`'s early-exit templates, and `init()`'s catch) shows `fileProtocolNote()` — the single highest-value diagnostic in the app, since a `file://` origin is null and silently blocks both Geolocation and every `content.osu.edu` fetch, which is what "the app only ever shows the timetable" reports usually turn out to be. Worded device-agnostically (this is meant to eventually run on a phone, where there's no terminal): the headline instruction is "open it from a web address", with the desktop-only `python3 -m http.server` command folded in as a parenthetical, not the main advice.

## Key constraints from prior decisions

- OSU publishes an unauthenticated, CORS-enabled bus API at `content.osu.edu/v2/bus` (plan §2). It needs no key, no OSU login and no proxy capture, which retires both the Proxyman plan and the "what if it needs the user's OSU credentials" pause-point.
- Treat that API as the source of truth for routes and stops. Where it disagrees with hand-entered values, the API wins — the hand-transcribed Arps Hall entry claimed five routes when the API serves two.
- Prefer baked-in generated data over fetching at load, so the app still works offline; regenerate via `tools/fetch-cabs-data.js`.
- Search on cheap local estimates, spend real routing calls only on the chosen itinerary. A public routing instance's rate limit is small enough that a search-time network call silently degrades every result to a straight line.
- Prefer keyless, CORS-clean services the user never has to configure — Esri's gray-canvas tiles, the OSU bus API, and now FOSSGIS's OSRM instances (`routing.openstreetmap.de`) and Valhalla (`valhalla1.openstreetmap.de`) all follow this. A provider that hides its error status behind a missing CORS header (OpenRouteService did this) will fail silently and waste an afternoon; check `access-control-allow-origin` on an *error* response, not just a successful one, before adopting one. A provider can also just never answer at all — Valhalla did this during an earlier outage (hanging past 12s), which is why it's kept only as a fallback tier behind FOSSGIS rather than the primary — that's what `fetchWithTimeout` + the per-tier circuit breakers in §2 are for.
- Never ask a routing provider for a profile it doesn't actually serve, and never assume a provider's stated duration for one profile is valid for another. The old `router.project-osrm.org` demo silently ignored everything but `driving` — every profile returned byte-identical car-road results, so a "foot" duration derived from it was really a car-road distance dressed up with a walking-speed formula, overstating campus walks by up to 2x because pedestrians cut across campus where cars must go around. FOSSGIS's `routed-foot` and `routed-car` (and Valhalla's `pedestrian`/`auto` costing) are genuinely distinct routed profiles, so their own reported durations can be trusted directly — verify what a provider's profiles actually return (byte-diff two profile responses, or compare against a known walk vs. drive time for the same pair) rather than trusting the URL parameter to mean anything.
- Verify browser-facing behaviour in a real browser. `curl` does not perform CORS, and a Node `fetch` stub does not enforce it, so both happily pass while the page fails.
